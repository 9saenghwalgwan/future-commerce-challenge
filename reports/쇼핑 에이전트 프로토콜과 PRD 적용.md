# 표준이 비워둔 '내 결제금액'을 증명하라

2026-11-22 기준으로 UCP·ACP·AP2·카드 네트워크 프로그램은 **판매자가 계산하는 가격(회원가·쿠폰·배송비·세금)**과 **결제 직전 사용자 확인**까지는 표준화했다. 그러나 **카드 청구할인, 전월실적, 무이자 할부, 포인트 가치, 판매처 간 비교, 관세는 어떤 스펙에도 없다**. 그래서 "UCP가 와도 사용자 맥락을 쥔 사용자 편 에이전트는 남는다"는 팀 논지를 감이 아니라 **스펙 필드 수준에서** 보여줄 수 있다. L1(결제 직전 멈춤)은 업계 기본값과 그대로 겹친다. UCP `requires_buyer_review`, ChatGPT Wallet의 건별 생체 승인, Shopify의 "구매자가 총액 확인 후", 네이버·카카오의 "최종 승인은 이용자"가 모두 같은 지점에서 멈춘다. 한국 현행법에서도 L1은 마찰이 가장 적은 설계다. L2(조건부 자동결제)는 AP2 v0.2의 open mandate, Stripe SPT식 한도·철회, 국내 카드사의 2027년 상반기 에이전트 페이 목표에 올려 **로드맵으로 정직하게** 그리면 된다. 쿠팡·네이버는 외부 에이전트를 제한한다고 보도됐고 개인화 가격 API도 없다. 따라서 **사용자 본인 기기의 로그인 결제창을 읽는 것**이 한국에서 '내 가격'을 얻는 유일한 현실 경로다. 심사위원사 가운데 KSNET(2026-09-30)과 NHN KCP(2026-11-18)는 AP2+x402 에이전트 결제를 실증했고, 둘 다 "비교 → 이용자 승인 → 결제" 흐름이라 우리 L2와 바로 이어진다. 주의할 점이 하나 있다. **AIR+Minds+Pivota+Reap 파일럿(2026-10-08 발표)**이 "검증된 속성 → 개인화 오퍼·가격 경로 → 범위 제한 결제" 개념에서 우리와 겹친다. 차별점은 다음 네 가지로 좁혀 말해야 한다. 판매자 통합 없이 한국 폐쇄 플랫폼에서 실측한다. 발급사 쪽 조건(청구할인·전월실적)을 넣는다. 이해 단계 아티팩트가 있다. 결제 직전 멈춤이 기본값이다. 오늘 현장 강의도 같은 방향을 가리켰다. Google Cloud는 '에이전트 결제 5단계'와 'AP2 = 체크카드 한도 설정 + 위임장'이라는 틀을 제시했고, Animoca Brands는 '4가지 질문(신뢰·보안·분쟁·닫힌 결제)'과 '결제 방식 3분류'를 제시했다. 두 강의 모두 결론을 **통제·위임·신뢰**에 두었고 **사용자 쪽 가격은 다루지 않았다**. 심사위원도 들은 이 언어로 L1/L2를 설명하면 바로 읽힌다(2절).

## 2. 해커톤 강의와의 연결: 심사위원이 오늘 들은 언어로 말한다

오늘 현장 강의는 두 개였다. Google Cloud의 '에이전트 경제와 오픈 프로토콜'과 Animoca Brands의 '에이전트 커머스와 신뢰'다. 둘 다 STT 녹취를 정리한 것이고 발언 내용은 독립 검증하지 않았다. 그래도 핵심 틀 상당수가 리서치 결과와 맞아떨어진다. Google 강의는 **통제(AP2)와 정산(x402)**을 결합해 "예산을 넘으면? 엉뚱한 결제를 하면 누가 책임지나?"에 답하겠다고 했다. Animoca 강의는 업계 공통 고민이 결제 레일이 아니라 **"에이전트 뒤에 진짜 사람이 있고 그 사람이 승인했는가"**로 모인다고 진단했다 [강의 발언(미검증)]. 두 강의 모두 "어떤 상품을 어디서 어떤 카드로 사면 *이 사용자에게* 실제로 얼마인가"는 다루지 않았다. 강의의 틀을 빌려 위임·신뢰를 설명하고, 그 틀이 비워둔 칸(이해와 진짜 가격)을 우리 자리로 보여주는 것이 '적시적소' 전략이다 [추론].

## 3. 4개 레이어 배치: 지금은 화면 실측, 프로토콜은 로드맵 칸에

핵심 구분은 **L1 시연에서는 에이전트가 판매자에게 자체 요청을 보내지 않는다**는 사실이다. 주문 요청을 보내는 것은 공식 쿠팡·네이버 iOS 앱이고, 사용자 세션 아래에서 움직인다. 그래서 Web Bot Auth·Visa TAP·KYA처럼 "에이전트가 서명한 HTTP 요청"을 전제로 한 판매자 쪽 검증 표준은 L1에 해당하지 않는다. 이 표준들은 에이전트가 판매자와 직접 대화하거나(MCP/UCP/A2A) 자율 결제할 때(L2)에 의미가 생긴다 [추론] ([Cloudflare: Securing agentic commerce](https://blog.cloudflare.com/secure-agentic-commerce)). 한국 커머스는 MCP를 일부 열고 있다. 무신사·롯데온·CJ올리브영은 MCP 서버를 구축했거나 구축 중이지만, 쿠팡·네이버 공개 MCP·UCP·A2A 인터페이스는 찾지 못했다 [보도] ([바이라인네트워크, 2026-05](https://byline.network/2026/05/28_129874/)). 화면 실측은 **영구 설계가 아니라 다리(bridge)**라고 설명해야 앞뒤가 맞는다.

| 레이어 | 지금 (L1 시연 범위) | 로드맵 (L2·확장) | 관련 표준과 상태 | 발표용 정직한 문장 |
|---|---|---|---|---|
| **신원·권한** | 사용자가 쿠팡·네이버 앱에 본인 로그인. 에이전트는 사용자 Mac에서 사용자 iPhone을 조작하고 자체 판매자 자격증명이 없음. "어떤 앱·화면을 열어도 되는지" 세션 접근 동의 카드 | AIR Identity로 "멤버십 보유·카드 보유"를 원본 노출 없이 yes/no로 선택적 공개. AIR Agent로 에이전트와 사용자를 묶고 범위 권한 부여. 에이전트가 직접 요청할 때는 Web Bot Auth/TAP 서명 | AIR(파트너 정의, 파일럿 설계 단계) [1차/보도], AP2 v0.2 SD-JWT mandate [1차], Web Bot Auth(IETF WG 채택 보도 2026-09-01) [2차], Visa TAP(2025-10-14, 베타) [1차] | "L1에서 판매자가 보는 주체는 사용자 본인입니다. 신원은 '누구인가'와 '무엇을 해도 되는가'를 별도 행으로 다룹니다." |
| **AI 에이전트** | 온디바이스 오케스트레이터와 내부 도구(아이폰 조작, 가격 계산기, 카드 규칙 DB, 아티팩트 생성기). **LLM은 조건 추출·설명만 하고 금액 계산은 결정론적 코드가 한다** | 내부 도구를 MCP 서버로 노출. Minds 같은 지속형 에이전트가 가격·조건 변화를 지켜봄(제안). A2A로 판매자·브랜드 에이전트와 대화 | MCP 2026-07-28 스펙 [1차], A2A v1.0(AAIF 소속, 2026-08) [1차/보도], AG-UI 1.0 [2차] | "비결정적인 AI는 제안만 하고 검증은 코드가 합니다(AP2 원칙과 동일)." |
| **커머스** | 쿠팡·네이버 **로그인 결제창 화면 읽기**(바로구매 경로, 결제 버튼 직전까지). 개인가를 주는 API·MCP·UCP는 없음 | UCP/ACP를 연 판매자에게는 identity linking(OAuth) 후 checkout session의 `totals`/`discounts`/`fulfillment`를 직접 읽는 어댑터. MCP를 연 국내 커머스부터 적용 | UCP v2026-08-25 [1차], ACP 2026-04-17 [1차] | "Google UCP도 회원가는 결제 단계에서만 보여줍니다. 결제창 실측은 우회가 아니라 표준이 가는 방향입니다." |
| **결제** | **에이전트 결제 없음.** 사용자가 기존 카드·페이 앱 인증으로 직접 결제. 책임·분쟁 구조는 기존 그대로 | AP2 open mandate 위에 발급사 에이전트 토큰(Visa Intelligent Commerce·Mastercard Agent Pay. 국내 카드사 2027년 상반기 목표) 또는 결제사 한도 위임(카카오페이 PoC형). AP2+x402(KSNET·NHN KCP 실증) | AP2 v0.2 [1차], Stripe SPT(KR 미지원) [1차], Visa Agentic Ready(국내 발급사 6곳) [보도] | "L1에서 AI는 결제 권한이 없습니다. 승인은 쇼핑몰과 카드사의 기존 인증 화면에서 사용자가 직접 합니다." |

UCP 자체가 "결제 단계에서만 회원가를 본다"는 점은 우리 방식의 정당성을 뒷받침한다. Google 구현 문서는 로열티를 **"checkout에서만"**, 계정을 연결해 검증된 사용자에게만 지원한다. 개인화 검색 결과는 "향후 릴리스"로 미뤘다 [1차] ([Google UCP loyalty overview](https://developers.google.com/merchant/ucp/guides/overview/loyalty)). 회원가를 보려면 구매처마다 checkout session을 열어야 한다는 뜻이고, 이는 후보×구매처마다 로그인 결제창에 들어가는 우리 방식과 같은 구조다 [추론].

### Google '에이전트 결제 5단계'로 다시 읽은 4레이어

Google 강의의 5단계는 주최 측 4단계와 거의 일대일로 겹친다 [강의 발언(미검증)]. 발표 결제 슬라이드는 이 순서를 따르고, 단계마다 "L1에서 하는 일 / L2에서 하는 일"을 나란히 두면 심사위원이 익숙한 순서로 읽는다.

| Google 5단계 | 주최 측 레이어 | 우리 L1 (지금) | 우리 L2 (로드맵) | 국내 실증 연결 |
|---|---|---|---|---|
| ① 의도 정의 | AI 에이전트 | **① 이해 단계**: 선언을 기준 발견으로 완성하고, 후보별 세팅·사용 결과와 유지·제외 근거를 정리 | 같은 과정에서 open mandate 조건 초안(판매처·상품·청구 금액 상한·기한)을 생성 | — |
| ② 권한 위임·서명 | 신원·권한 | **결제 권한 위임 없음.** 세션 접근 동의(어떤 앱·화면을 열어도 되는지)만 받음 | AP2 open mandate를 에이전트가 아닌 화면에서 생체·패스키로 서명(AIR 범위 권한) | KSNET: 이용자 승인·서명에 AP2 사용(2026-09-30) [2차] |
| ③ 가맹점 연결·청구 | 커머스 | **② 진짜 가격 단계**: 사용자 앱 결제창에 들어가 실측하고, **청구 직전에 멈춤** | 결제창 재확인 → 결정론적 검사기 통과 시에만 청구 | Visa Agentic Ready 2단계 테스트 항목: 상품 선택→장바구니→결제→정산 [보도] |
| ④ 퍼실리테이터(중개·검증) | 결제 | 해당 없음(기존 PG·카드사 인증이 처리) | PG·네트워크가 mandate·에이전트 토큰을 검증 | NHN KCP: x402 퍼실리테이터 자체 구현(2026-11-18) [2차] |
| ⑤ 최종 정산·집행 | 결제 | 기존 카드망 정산(**범위 밖**) | 카드 에이전트 토큰, 또는 입법 후 스테이블코인 레일 | KSNET: KSPAY 원화 정산 구조 [2차] |

## 4. 위임 설계: L1은 사람이 closed mandate에 서명하고, L2는 open mandate 안에서만 움직인다

### AP2는 v0.2에서 어휘가 바뀌었다

2026년 기사 상당수는 아직 AP2 v0.1(2025-09-16)의 Intent/Cart/Payment 세 mandate로 설명한다. 그러나 **v0.2(2026-04-28)**는 이를 **Checkout Mandate와 Payment Mandate 두 종류**로 바꿨고, 각각에 **open(사전 서명한 제약)**과 **closed(특정 거래 1건)** 형태를 두었다. 둘 다 SD-JWT 검증가능 자격증명이다 [1차] ([AP2 CHANGELOG](https://github.com/google-agentic-commerce/AP2/blob/main/CHANGELOG.md); [AP2 v0.2 specification](https://github.com/google-agentic-commerce/AP2/blob/main/docs/ap2/specification.md)). Google은 2026-04-29 AP2를 FIDO Alliance에 기증했다 [보도] ([FIDO Alliance](https://fidoalliance.org/google-donates-agent-payments-protocol-to-fido-alliance/)). GitHub에는 태그 릴리스와 PyPI 패키지가 없고 04-29 이후 커밋도 없다. 그러니 **참조 설계로 인용하고 '배포된 레일'이라고 하지 않는다** [1차/추론] ([AP2 GitHub](https://github.com/google-agentic-commerce/AP2)).

v0.2의 원칙 세 가지가 우리 설계와 정확히 맞물린다. 첫째, 사용자 동의를 받는 **Trusted Surface는 "MUST be non-agentic"**이다. 둘째, 쇼핑 에이전트는 "잠재적 공격자"로 가정하므로 **모든 검증은 결정론적 코드로 한다**. 셋째, 제약을 검증할 수 없으면 `unresolved_constraint` 오류로 **사람을 다시 불러들인다** [1차] ([AP2 specification](https://github.com/google-agentic-commerce/AP2/blob/main/docs/ap2/specification.md); [flows](https://github.com/google-agentic-commerce/AP2/blob/main/docs/ap2/flows.md)).

| 단계 | 에이전트가 하는 일 | AP2 v0.2 대응 | 결제 쪽 통제 | 사용자 확인 | 상태 |
|---|---|---|---|---|---|
| **L0 조언** | 비교·설명만. 세션 접근 없음 | mandate 없음 | 없음 | 없음 | 가능 |
| **L1 결제 직전 멈춤** (기본·시연) | 로그인 결제창까지 들어가 실제 최종 금액(쿠폰·배송·결제수단 할인)을 구성한 뒤 **멈춤** | **Human Present**: AP2가 말하는 closed Checkout을 만든 상태. 사용자가 쇼핑몰 결제 버튼과 카드·페이 앱 인증(= Trusted Surface)으로 직접 승인 | 기존 카드 인증(ISP·앱카드·3DS), 기존 분쟁 절차 | 매 거래 | **시연** |
| **L2 조건부 자동결제** (로드맵) | open mandate 범위 안에서, 실행 직전 결제창을 다시 읽고 **결정론적 검사기가 모든 제약을 통과시킨 경우에만** 실행. 아니면 L1로 복귀 | **Human Not Present**: open Checkout(`allowed_merchants`, `line_items.acceptable_items`) + open Payment(`amount_range`, `execution_date`, `allowed_payment_instruments`, `budget`/`agent_recurrence`). 에이전트는 `cnf`로 묶인 자기 키로 closed mandate에 서명. 실패하면 `unresolved_constraint` → 사람 | SPT식 단일 판매자, `max_amount`, `expires_at`, 즉시 철회(revoke) | 사전 1회(생체·패스키, 에이전트가 아닌 화면) | 2027년 이후, 혁신금융서비스 대상 |

AP2 v0.2 open mandate의 제약 목록은 "총액 N원 이하일 때만, 판매처 M에서, D일까지 X를 산다"를 거의 그대로 표현한다 [1차] ([payment_mandate](https://github.com/google-agentic-commerce/AP2/blob/main/docs/ap2/payment_mandate.md); [checkout_mandate](https://github.com/google-agentic-commerce/AP2/blob/main/docs/ap2/checkout_mandate.md)). Stripe SPT는 실제 운영 중인 범위 제한 위임의 가장 구체적인 사례다. 판매자 1곳, `usage_limits[max_amount]`·`[currency]`·`[expires_at]`, 언제든 철회(`/revoke`), 사용·비활성 웹훅을 갖췄다. **지원 국가에 한국은 없다** [1차] ([Stripe SPT docs](https://docs.stripe.com/agentic-commerce/concepts/shared-payment-tokens)).

### Animoca '결제 방식 3분류'에서 우리 위치

Animoca 강의는 에이전트 결제를 세 유형으로 나누고, 앞의 두 유형은 "사용자 승인 문제를 풀지 못해 생긴 형태"라고 봤다 [강의 발언(미검증)]. 우리 L1은 이 셋 어디에도 딱 들어맞지 않는다. 자격 정보를 넘기지 않고, 웹으로 링크아웃하지도 않으며, 승인을 위임받지도 않는다. **사용자 본인 앱의 실제 결제창까지 들어가 실측한 뒤 결제 버튼 앞에서 멈추는 네 번째 위치**다. 이 점을 도식으로 보여주면 설득력이 크다 [추론].

| 유형 (연사 분류) | 방식 | 리스크·한계 (리서치) | 우리 위치 |
|---|---|---|---|
| 자격 정보 위임형 (연사 예시 '피클', 서비스 미확인) | 클라우드 서버가 사용자 비밀번호 등을 넘겨받아 결제 | 국내법상 접근매체 사용 위임은 이용자 중과실 유형이라 사고 손실이 이용자에게 돌아갈 위험 [보도] ([법률신문](https://www.lawtimes.co.kr/news/articleView.html?idxno=229080)) | **하지 않음.** 비밀번호·PIN·인증수단을 받지 않음 |
| 링크아웃형 (연사 예시 GPT) | 판매처로 이동해 사용자가 직접 결제 | 이탈이 생기지만 안전. OpenAI도 2026-03 이 방식으로 돌아섬 [보도] ([Modern Retail](https://www.modernretail.co/technology/what-went-wrong-with-chatgpts-instant-checkout/)) | **L1은 링크아웃의 안전성을 유지하되**, 공개 페이지가 아니라 사용자 로그인 결제창에서 실측해 가격 분해를 함께 넘김 |
| 승인 위임형 (연사 예시 Minds) | 사용자 승인을 위임받아 앱 안에서 결제 | 승인 범위의 증명과 철회가 핵심. AP2 Human Not Present, Reap 범위 제한 결제수단과 같은 구조 [1차/보도] | **L2 로드맵**: AIR 범위 권한 + AP2 open mandate + 발급사 토큰 |

### L2 조건은 두 칸으로 나눠야 한다

결제망이나 PG가 강제할 수 있는 숫자는 **실제 청구 금액**(`payment_amount`)뿐이다. 판매자 쿠폰과 배송비가 반영된 금액이다. 카드 **청구할인, 적립, 무이자 효과는 `payment_amount`에 들어가지 않는다** [1차/추론] ([AP2 payment_mandate](https://github.com/google-agentic-commerce/AP2/blob/main/docs/ap2/payment_mandate.md)). 그래서 L2 조건은 (a) **청구 금액 상한 X원**(결제 레일이 강제)과 (b) **"청구할인·적립 반영 실질가 ≤ Z원"**(에이전트가 검사하고 기록하지만 결제망이 강제하지는 않음)으로 나눠 표기한다. 이 구분 자체가 "프로토콜이 생겨도 사용자 편 에이전트만 계산할 수 있는 숫자가 남는다"는 논지의 두 번째 증거다 [추론].

### 권한 카드(L2)와 결정 영수증(L1·L2 공통)

Google 강의는 AP2를 **"얼마까지 써도 되는지 정하는 체크카드 한도 설정 + 위임장 발급"**에 비유했다 [강의 발언(미검증)]. 권한 카드는 그 '한도 + 위임장'을 사용자 화면으로 옮긴 것이라고 소개하면 된다. 한 줄은 꼭 덧붙인다. 비유 속 '한도'는 결제망이 강제할 수 있는 **청구 금액**에만 걸리고, 청구할인 반영 실질가는 에이전트가 검사하는 별도 칸이다.

| 권한 카드 행 | 내용 | 대응 필드 |
|---|---|---|
| 어디서 | 쿠팡 / 네이버 스마트스토어 ○○ | `checkout.allowed_merchants` |
| 무엇을 | 정확한 상품·옵션(예: KVM 2개 모델 중 1개), 수량 1 | `checkout.line_items.acceptable_items` |
| 얼마까지 | **청구 금액 상한**(배송비 포함·쿠폰 적용 후인지 명시) + 실질가 조건(에이전트 검사 표시) | `payment.amount_range` |
| 언제까지 | 만료 일시(가능한 한 짧게) | `payment.execution_date.not_after`, `exp` |
| 어떤 결제수단 | 카드명과 끝 4자리 | `payment.allowed_payment_instruments` |
| 몇 번 | 1회 또는 반복(총예산) | `payment.agent_recurrence`, `payment.budget` |
| 조건 밖이면 | **멈추고 다시 물어봄(변경 불가)** | `unresolved_constraint` |
| AI가 할 수 없는 것 | 다른 상품 대체, 수량 변경, 새 카드 등록 금지 | 범위 밖 |
| 상태·철회 | 대기 / 실행됨 / 만료 / 철회 + **즉시 철회** 버튼 | SPT revoke, webhooks |

L1에는 결제 권한 카드가 필요 없다. 대신 "L1: 결제 직전 멈춤" 배지와 세션 접근 동의 카드를 보여준다. 탐색 중 / 결제 권한 사용 중 상태 표시는 Visa TAP·Mastercard Agent Pay가 서명 태그로 구분하는 `agent-browser-auth`/`agent-payer-auth`를 사용자 화면에 옮긴 것이다 [1차] ([Cloudflare](https://blog.cloudflare.com/secure-agentic-commerce)).

**결정 영수증**은 실행마다 다음을 위·변조 확인이 가능하게(해시 체인 또는 서명) 남긴다. 사용자가 승인한 조건과 그 해시, 에이전트가 본 결제창 스냅샷(화면 캡처 또는 해시, 품목, 가격 분해, 시각), 조건별 통과·실패, 실행한 행동(L1 멈춤 / L2 실행), 주문번호. AP2는 Checkout·Payment Mandate와 Receipt를 합쳐 "부인할 수 없는 거래 기록"을 분쟁 증거로 쓰도록 설계했다 [1차] ([AP2 specification](https://github.com/google-agentic-commerce/AP2/blob/main/docs/ap2/specification.md)). FTC 위원장도 "audit trails tell the real story"라고 말했다 [2차] ([Chargeflow](https://www.chargeflow.io/blog/agentic-commerce-regulation-what-merchants-need-to-know)). 한계도 정직하게 적는다. **쿠팡·네이버는 제3자 에이전트를 위해 결제를 서명해 주지 않는다.** 그래서 AP2의 판매자 서명 Checkout JWT 대신 에이전트가 찍은 스냅샷과 해시를 증거로 쓴다 [추론].

### 책임 구조: L1이 '안심'의 가장 강한 답인 이유

에이전트 거래 전용 차지백 사유 코드나 책임 이전(liability shift)은 아직 없다. Visa 규칙은 "카드 소지자가 Agentic Payment Provider의 행위에 책임진다"는 취지로 알려져 있다 [2차] ([Chargeflow](https://www.chargeflow.io/blog/ai-agent-chargeback-liability)). Target은 2026-03-22 약관을 개정해 Gemini 에이전트 거래를 "당신이 승인한 거래"로 간주한다 [보도] ([eMarketer](https://www.emarketer.com/content/target-limits-liability-ai-shopping-assistants-gain-traction)). 에이전트 오류에 대한 소비자 보호를 명시한 곳은 Amex Agent Purchase Protection 하나이고, **미국 신용카드에만** 적용된다 [보도] ([Digital Commerce 360, 2026-04-14](https://www.digitalcommerce360.com/2026/04/14/american-express-agentic-commerce-developer-kit-purchase-protection/)). 한국 법률 분석도 같은 결론이다. AI 오작동·프롬프트 인젝션은 금융회사 무과실책임 사고 유형에 들어맞지 않을 수 있고, 정상 인증 거래로 기록되기 때문에 손실이 이용자에게 돌아갈 가능성이 크다 [보도] ([법률신문, 2026-11-09](https://www.lawtimes.co.kr/news/articleView.html?idxno=229080)). L1에서는 사용자가 자기 카드로 직접 결제하므로 **새로운 책임 문제가 생기지 않는다**. 이것이 "AI를 안심하고 맡길 수 있나요?"에 대한 가장 정직하고 강한 답이다 [추론]. Animoca 강의가 꼽은 '보안(카드를 맡길 수 없다)'과 '분쟁(승인 증거가 없다)' 질문에 대한 직접 답이기도 하다. Google 강의가 AP2+x402로 풀겠다고 한 "엉뚱한 결제를 하면 누가 책임지나"라는 질문을, L1은 애초에 생기지 않게 만든다 [강의 발언(미검증)/추론].

## 5. 진짜 가격 모델: 판매자 쪽은 프로토콜이 덮고, 사용자 쪽은 우리만 계산한다

UCP는 identity linking을 거치면 판매자 쪽 개인화를 상당 부분 다룬다. 검증된 회원가(`discounts.applied[]`, `provisional:false`), 멤버십 무료배송, 쿠폰 거절 사유 코드(`discount_code_user_not_logged_in`, `discount_code_user_ineligible` 등), 판매자가 비용을 대는 결제수단 혜택(**provisional** 할인), 적립 예상(`earning_forecast`), 배송 옵션별 비용·도착 시간이 있다 [1차] ([UCP discount extension](https://ucp.dev/latest/specification/shopping/extensions/discount/); [Google UCP loyalty implementation](https://developers.google.com/merchant/ucp/implementation/2026-04-08/loyalty)). ACP는 쿠폰·배송·세금·수수료와 판매자 측 포인트·상품권 결제수단을 다루지만 **로열티와 계정 연결 모델이 없다** [1차] ([ACP changelog 2026-04-17](https://github.com/agentic-commerce-protocol/agentic-commerce-protocol/blob/main/changelog/2026-04-17.md)). 두 프로토콜 모두 각 세션이 **판매자 1곳 단위**라서 판매처 간 비교는 원천적으로 에이전트 몫이다 [1차]. Google 강의는 UCP를 "모든 쇼핑몰을 하나의 방식으로 조회·주문"하게 해주는 표준으로 소개했다 [강의 발언(미검증)]. 조회 방식이 통일돼도 아래 매트릭스의 사용자 쪽 줄은 비어 있다. "UCP는 진짜 가격의 필요를 없애지 않고 오히려 드러낸다"는 말이 정확하다 [추론].

UCP 스펙은 우리 정직성 라벨의 근거도 준다. 결제수단 혜택 같은 구매자 주장은 판매자가 "MUST surface... as provisional discounts"로 표시하고, 플랫폼은 그 provisional 할인을 "MUST display"해야 하며, 결제 완료 시점에 해소해야 한다 [1차] ([UCP discount extension](https://ucp.dev/latest/specification/shopping/extensions/discount/)). 우리 "카드 X로 결제하면 Y원 청구할인"은 provisional(추정)이고, 로그인 결제창에서 읽은 금액은 verified(확인됨)다. **정직성 라벨은 표준 의미론과 맞춘 기능이 된다** [추론].

Bain도 "에이전트가 리워드를 보지 못하면 결제수단을 최적화할 수 없다"고 지적했다 [2차] ([Bain](https://www.bain.com/insights/how-card-issuers-and-banks-can-avoid-being-shut-out-of-agentic-commerce/)). 2026-11-13 출시된 ChatGPT Wallet도 카드 리워드를 **유지만 할 뿐 계산하지 않는다** [1차] ([OpenAI: Introducing ChatGPT Wallet](https://openai.com/index/introducing-chatgpt-wallet/)). 그래서 우리 주장은 "발급사 혜택 데이터를 가졌다"가 아니라 **"판매자가 실제로 계산한 결제창을 읽고, 발급사 규칙은 근거와 함께 추정으로 표시한다"**여야 한다.

한국 쪽 데이터 경로도 정리해 둔다. 결제창 가격·쿠폰·멤버십가는 iPhone Mirroring으로 로그인 화면을 읽는 것이 현실적으로 유일한 경로다. 카드 혜택 규칙은 카드사 공개 상품설명서로 규칙 DB를 만든다. 전월실적은 카드 앱 실적 화면을 읽거나 사용자에게 입력받는다. 마이데이터 표준 API에 혜택·실적 항목이 있는지는 **확인하지 못했으므로 PRD에 '검증 필요'로 적는다** [추론]. 관세청의 "150달러 초과 시 공제 없이 전액 과세" **절벽 구조**는 진짜 가격을 시연하기 좋은 사례지만, 환율 적용일과 합산과세 규칙은 재확인해야 한다 [1차/추론] ([관세청](https://www.customs.go.kr/kcs/ad/tax/BuyTaxCalculation.do?mi=2853)).

## 6. 결정 보드: 경쟁 제품이 보여주지 않는 다섯 가지를 보여준다

### 사용자는 AI를 쓰고 나서 오히려 더 검증한다

IAB×Talk Shoppe 연구(450여 개 화면 녹화 세션, 미국 n=600)를 보면, AI를 쓴 뒤 쇼핑 단계는 **1.6단계에서 3.8단계로 늘었고 95%가 확신을 얻으려고 추가 단계를 밟았다**. 신뢰가 깨진 지점은 **출처 누락, 사양·가격 불일치, 오래된 재고 정보, 예산·호환성 불일치**였다 [보도] ([Search Engine Journal, 2025-10-28](https://www.searchenginejournal.com/trust-in-ai-shopping-is-limited-as-shoppers-verify-on-websites/559497/)). 이 결과는 속도를 성공 기준으로 삼지 않는 팀 방침과 맞는다. 사용자가 늘어난 단계를 검증에 쓴다면, **그 검증을 에이전트 화면 안으로 가져오는 것**이 가치다 [추론]. Google 강의의 '간접 신호 → 직접 선언' 틀도 여기서 쓸 수 있다. 사용자가 프롬프트로 원하는 것을 직접 말하는 시대라는 진단이다 [강의 발언(미검증)]. 하지만 IAB 연구의 신뢰 붕괴 요인인 예산·호환성 불일치는 **선언이 불완전하다**는 신호다. 그래서 보드 맨 위의 '요청 조건 체크리스트'는 사용자가 말한 조건만 담지 않는다. 에이전트가 기준 발견 단계에서 찾아낸 조건(KVM이라면 포트·케이블·사용 환경)을 "에이전트가 추가한 기준"으로 따로 표시한다 [추론]. 위임 의향 데이터도 L1 기본값을 지지한다. Riskified(n=5,100, 2026-10-27)에서는 **43%가 모든 구매를 직접 승인하길 원했고**, 29%는 자기 규칙 안의 자동구매를 허용했으며, **7%만** 승인 없는 구매를 편하게 여겼다 [1차] ([Riskified](https://www.riskified.com/press/agentic-commerce-pulse-consumer-survey-november-2026/)). Accenture(n=25,590)에서는 32%가 "AI가 정하고 소비자가 결제"를, 9%가 가드레일 안 자율구매를 받아들였다 [2차] ([Accenture](https://www.accenture.com/gb-en/insights/consulting/talk-my-ai-agent)).

### 경쟁 제품이 보여주지 않는 것과 우리 보드 요소

ChatGPT 쇼핑 리서치, Google AI Mode, Perplexity, Amazon Help Me Decide는 모두 **상품 카드 + 구매 가이드 요약**으로 수렴했다. 불확실성은 "가격과 재고에 오류가 있을 수 있으니 판매처를 확인하라"는 **페이지 단위 면책 문구**로 처리한다 [1차] ([OpenAI shopping research](https://openai.com/index/chatgpt-shopping-research)). 검토한 자료 범위에서는 다섯 가지가 보이지 않았다. 사용자별 최종 가격, 에이전트가 직접 뺀 후보와 그 이유, 필드 단위 확인·추정 구분, 사용 후 환경, 탐색 범위다 [추론].

| 보드 요소 | 무엇을 보여주나 | 겨냥하는 신뢰 붕괴 요인 | 비고 |
|---|---|---|---|
| **요청 조건 체크리스트** | 사용자 조건마다 후보별 충족 / 미충족 / 모름 | 예산·호환성 불일치 | |
| **탐색 범위** | 조사한 구매처·출처, 찾은 개수, **못 본 곳과 이유**(접근 불가·품절) | 출처 누락 | 이 요소를 보여주는 제품을 찾지 못함 |
| **제외 후보와 이유** | 에이전트가 뺀 후보와 사유 태그(포트 불일치, 예산 초과, 배송 7일 초과) + 복원 버튼 | 설명 부재 | ChatGPT의 "Not interested"는 사용자가 빼는 방향만 있음 |
| **필드 단위 3상태 라벨** | ✅ 확인됨(URL·시각) / ◐ 추정("카드 X 보유 가정") / ? 미확인. 가정을 화면에서 바로 고치면 재계산 | 사양·가격 불일치 | 페이지 단위 면책 문구만 쓰는 방식은 피함 |

### A2UI·AG-UI·MCP Apps는 "착안"으로만 인용한다

세 표준은 결정 보드의 설계 근거로 쓸 만하다. 그러나 실제로 쓰지 않았다면 "준수"나 "기반"이라고 말하면 안 된다. 주최 측 심사에는 특정 기술 사용 의무가 없으므로, 정직하게 표현해도 잃는 점수는 없다.

| 표준 (상태) | 빌려올 개념 | PRD에 쓸 표현 | 쓰면 안 되는 표현 |
|---|---|---|---|
| **A2UI v0.9** (2026-04-17. v1.0은 RC라는 2차 보도) | "UI를 코드가 아닌 데이터로", 클라이언트가 승인한 **컴포넌트 카탈로그**만 조합, 권한·기기에 따라 바뀌는 동적 카탈로그, 클라이언트 쪽 검증 함수 [1차] ([A2UI README](https://github.com/google/A2UI/blob/main/README.md); [Google Developers Blog](https://developers.googleblog.com/a2ui-v0-9-generative-ui/)) | "A2UI의 선언형 카탈로그 방식에서 착안해, 에이전트는 사전 승인된 아티팩트 컴포넌트(`KvmConnectionDiagram`, `PriceBreakdown`, `EvidenceItem` 등)만 조합한다. 그래서 상품마다 아티팩트가 달라져도 안전하고 일관된다" | "A2UI 준수/호환"(실제 스키마나 렌더러를 쓰지 않았다면) |

| **MCP Apps** (2026-01-26, 첫 공식 MCP 확장) | `ui://` 리소스를 샌드박스 iframe에서 렌더링, 미선언 도메인 차단, UI가 시작한 도구 호출에 **호스트가 사용자 승인을 요구** 가능 [1차] ([MCP blog](https://blog.modelcontextprotocol.io/posts/2026-01-26-mcp-apps/)) | "확장 범위: 결정 보드를 MCP App으로 포장하면 Claude·ChatGPT 같은 호스트 안에서도 렌더링할 수 있다" | "ChatGPT/Claude에서 동작한다" |

한 가지 원칙은 세 표준 모두와 맞는다. **금액 계산은 결정론적 엔진, LLM은 조건 추출과 설명.** Google의 완전 생성형 UI(dynamic view)는 생성에 "1분 이상"이 걸리고 "가끔 부정확"하다고 스스로 밝혔다 [1차] ([Google Research](https://research.google/blog/generative-ui-a-rich-custom-visual-interactive-user-experience-for-any-prompt/)). 가격이 중요한 보드에는 카탈로그형이 방어하기 쉽다 [추론].

### AIR 파일럿과의 겹침: 정직하게 다르게 말하는 법

2026-10-08 Animoca가 발표한 흐름은 이렇다. AIR가 사용자 속성을 검증하고, 사용자가 Minds 에이전트에 선택적으로 공유하고, 에이전트가 오퍼 자격을 암호학적으로 증명하고, Pivota가 상품·판매처·경로를 고르고, Reap이 판매처·금액·기간으로 제한된 결제 자격증명을 발급하고, 사전 승인 한도 안에서만 거래한다. 상태는 **"단일 판매자 통합의 통제된 시연으로 시작"**하는 제안 아키텍처이고 한국은 언급되지 않았다 [보도] ([Animoca Brands](https://www.animocabrands.com/announcement/animoca-brands-air-and-minds-partner-with-reap-and-pivota-to-enable-identity-powered-personalized-agentic-commerce); [The Paypers](https://thepaypers.com/payments/news/air-and-minds-partner-with-reap-and-pivota-on-agentic-commerce)). 오늘 Animoca 연사가 말한 "스테이블코인 카드 발급사, 결제사, 상품 인덱스·주문 라우팅 회사와의 파트너십 실증"은 이 발표 구성(Reap, Pivota)과 일치한다. 연사는 약 4개월 전 홍콩 구현본에서 앱 안 결제까지 이어지는 흐름을 영상으로 보여줬다고 했다 [강의 발언(미검증)]. 즉 심사위원 쪽에서도 "개인화 오퍼 + 범위 제한 결제" 구도를 이미 알고 있다고 보고 차이를 설명해야 한다. 심사위원 중 Animoca Brands Growth Lead가 있으므로 "우리가 더 낫다"보다 **"같은 방향의 한국형 앞단이자 L1 단계"**로 위치시키는 편이 정직하고 유리하다.

| 겹치는 개념 | 그 파일럿 | 우리의 정직한 차이 |
|---|---|---|
| 개인화 가격 경로 | Pivota가 판매자 스택을 통해 누적 프로모션·배송까지 맞춘 경로를 선택 | 판매자 **통합 없이** 사용자 로그인 결제창에서 실측. 쿠팡·네이버처럼 인덱스·API가 열리지 않은 폐쇄 플랫폼 대상 |
| 사용자 조건 | AIR 검증 속성·자격(오퍼 자격) | **발급사 쪽 조건**(청구할인·전월실적·무이자)과 결제수단별 혜택까지. 단, 계산은 추정으로 표시 |

| 사용자 이해 | 공개 자료 없음 | ① 이해 단계: 기준 발견, 세팅·사용 결과, 유지·제외 근거를 상품별 시각 아티팩트로 제공 |

한 줄 요약: "AIR가 '누가, 무엇까지'를 증명하는 신원·권한 레이어라면, 우리는 한국 사용자가 '무엇을, 어디서, 어떤 카드로' 살지 이해하고 진짜 가격을 확인하는 앞단입니다. L2에서는 AIR 범위 권한 위에서 동작하도록 설계했습니다." "AIR 연동 완료"나 "Minds가 지갑을 감시한다"는 말은 하지 않는다. Minds 제품 사이트(BETA)는 쇼핑·지갑·모니터링 기능을 광고하지 않는다 [1차] ([hellominds.ai](https://hellominds.ai)). "Minds 같은 지속형 에이전트가 가격·조건 변화를 지켜보는 역할(제안)"로만 말한다. 연사는 Minds가 사용자를 기억하고 먼저 제안한다고 했다(이메일 연동 후 다음 날 발표 자료를 먼저 제안한 예) [강의 발언(미검증)]. 이 성질은 [A-편리·재방문]의 로드맵 근거로 쓸 수 있다. 예를 들어 "찜한 KVM이 진짜 가격 기준으로 내려가면", "이번 달 전월실적이 충족되면" 먼저 알리는 역할이다. 연사가 말한 카카오톡 연동은 리서치에서 확인하지 못했다(사이트에서는 텔레그램만 확인). 연사가 "백엔드 LLM이 비슷해서 에이전트들이 다 비슷하다"며 차별점을 신원에서 찾은 것도 활용할 수 있다. 우리는 차별점을 **이해(사용 결과 시각화)와 진짜 가격(결제창 실측)**에 두고, 신원은 AIR 같은 인프라에 맡기는 보완 관계로 말한다 [강의 발언(미검증)/추론].

"표시가 ≠ 실제 결제액"이 **정책으로 인정된 소비자 문제**라는 근거로 문제 정의에 인용할 수 있다.

미국 판례는 참고 맥락으로만 쓴다. Amazon v. Perplexity에서 지방법원은 2026-03-10 Comet에 가처분을 내렸지만, **제9순회항소법원이 2026-08-04 만장일치로 이를 파기했다**. 사용자 기기에서 도는 어시스턴트는 "사람이 아닌 도구"이고 접속 주체는 사용자라는 판단이다. 판결은 CFAA·CDAFA의 '접근' 요건에 한정되고, 약관·불법행위 쟁점은 열어둔 채 사건을 지방법원으로 돌려보냈다 [보도] ([Pearl Cohen](https://www.pearlcohen.com/ninth-circuit-vacates-injunction-against-perplexitys-ai-shopping-agent/); [MediaPost](https://www.mediapost.com/publications/article/417007/appeals-court-sides-against-amazon-lifts-perplexi.html)). 우리 구조(사용자 Mac → 사용자 iPhone → 사용자 로그인 앱, 에이전트와 판매자 사이 서버 통신 없음)는 법원이 우호적으로 본 사실관계에 가깝다. 그러나 **한국법상 방패가 아니다** [추론].

## 11. 예상 Q&A

**Q1. UCP가 퍼지면 결국 플랫폼이 다 해주지 않나요?** UCP와 ACP 스펙에는 카드 청구할인, 전월실적, 무이자, 포인트 가치, 판매처 간 비교, 관세 필드가 없습니다. UCP 회원가도 Google 구현에서는 "결제 단계에서만, 계정 연결한 사용자에게만" 보입니다. 실제 결제는 미국 소수 리테일러 중심이고 한국 판매자는 지원하지 않습니다. 프로토콜이 퍼지면 저희는 화면 실측 대신 그 API를 읽으면 되지만, 사용자 쪽 계산과 판매처 간 판단은 그대로 남습니다.

**Q2. 쿠팡·네이버가 막거나 약관 위반이면요?** 오늘 Animoca 강의에서도 나왔듯 플랫폼의 에이전트 차단은 실제 흐름입니다(아마존의 외부 에이전트 차단은 보도로 확인). 쿠팡이 외부 에이전트를 허용하지 않는다는 보도도 리스크로 명시했습니다. 차단이 생기는 이유는 대개 사람인지 봇인지 구분하지 못하기 때문인데, 저희는 서버에서 도는 봇이 아니라 사용자 본인 기기·본인 세션에서 움직입니다. 완화책은 네 가지입니다. 사용자 본인 기기·본인 세션에서만 돌고, 사람 수준 빈도로만 접근하고, 대량 수집을 하지 않고, 결제 버튼 직전까지만 읽습니다. 미국 제9순회항소법원은 2026-08 사용자 기기에서 도는 에이전트의 '접근 주체'를 사용자로 봤지만, 미국 판례이고 약관 쟁점은 열려 있어 방패로 쓰지 않습니다. 법률 검토 전에는 데모 범위로 한정하고, MCP·UCP를 연 판매자부터 프로토콜 어댑터로 옮겨가는 것이 로드맵입니다.

**Q3. 왜 꼭 AI 에이전트여야 하나요?** 후보 N개 × 구매처 M곳 × 결제수단 조건 K개를 로그인 세션마다 열어 확인하는 조합 작업이라 사람은 건너뛰고, 플랫폼 에이전트는 자기 몰 밖을 보지 않습니다. 여기에 "이 KVM을 내 맥북·모니터 환경에 연결하면 무엇이 더 필요한가" 같은 상황 해석이 붙어야 진짜 가격이 정해집니다. 규칙 계산은 코드가 하고, 조건 발견·해석·설명은 AI가 합니다.

**Q4. 자동결제가 없으면 편리하지 않잖아요?** 저희 가치는 속도가 아니라 결정의 질입니다. 조사에서 43%가 모든 구매를 직접 승인하길 원했고 승인 없는 구매를 편하게 여긴 비율은 7%였습니다(Riskified). AI를 쓴 뒤에도 사용자는 판매처에서 가격과 재고를 다시 확인합니다(IAB). 그 검증을 화면 안으로 가져오고, 쌓인 카드·멤버십 맥락으로 다음 비교가 더 정확해지는 것이 다시 찾을 이유입니다.

**Q5. 계산이 틀리면 누가 책임지나요?** L1에서는 사용자가 판매처 결제창에서 가격 분해를 보고 직접 결제하므로 기존 카드 거래와 책임 구조가 같습니다. 모든 값에 확인됨/추정/미확인을 붙이고, 넘겨주기 직전 결제창을 다시 읽어 차이가 있으면 경고합니다. 최저가나 최적은 보장하지 않습니다.

**Q6. L2는 어떻게 안전하게 하나요?** AP2 v0.2의 open mandate 구조를 따릅니다. 판매처·상품·청구 금액 상한·기한·결제수단을 사용자가 에이전트가 아닌 화면에서 생체 인증으로 승인합니다. 실행 직전 결정론적 검사기가 모든 조건을 확인하고, 하나라도 어긋나면 멈추고 다시 묻습니다. 즉시 철회와 결정 영수증을 둡니다. 결제 수단은 사용자 비밀번호가 아니라 카드사 에이전트 토큰(2027년 상반기 목표)이나 결제사 한도 위임 위에서만 쓰고, 현행법 근거가 없으므로 혁신금융서비스 대상으로 봅니다.

**Q7. 블록체인·스테이블코인은 어디에 쓰나요?** (KSNET·Animoca 대상) 오늘 Google 강의 결론대로 스테이블코인은 카드를 대체하지 않고 구간이 나뉩니다. 고액·저빈도·국내 거래는 기존 결제망이 유리하고, KVM 같은 국내 소비자 구매가 바로 그 구간입니다. 그래서 정산 레일은 이번 범위 밖입니다. 권한 증명 계층(서명된 범위 mandate, 선택적 공개 자격증명, 감사 기록)은 결제 레일과 무관하게 설계했습니다. x402는 API·디지털재화 소액결제에 맞고, 쿠팡·네이버 결제창의 핵심 수단은 카드·페이·포인트입니다. 카드 혜택 차이가 바로 저희가 계산하는 가치이기도 합니다. 원화 스테이블코인 입법 전이므로, KSNET·NHN KCP가 실증한 AP2+x402 레일은 L2에서 꽂을 수 있는 결제수단 유형으로 둡니다.

**Q8. 카드 혜택·전월실적 데이터는 어디서 오나요?** 시연에서는 카드사 공개 상품설명서로 만든 규칙과 사용자가 확인한 값을 '추정'으로 표시합니다. 중기에는 카드 앱 실적 화면 읽기와 마이데이터 사업자 제휴를 검토합니다. 마이데이터 표준 API에 혜택·실적 항목이 있는지는 확인이 필요하다고 PRD에 적었습니다.

**Q9. AIR+Minds+Pivota+Reap 파일럿과 뭐가 다른가요?** 오늘 강의에서 말씀하신 스테이블코인 카드 발급사·결제사·주문 라우팅 파트너십이 그 구성으로 알고 있습니다. 발표 자료 기준으로는 판매자 통합을 전제로 한 단일 판매자 시연 계획입니다. 저희는 통합 없이 한국 폐쇄 플랫폼에서 사용자 로그인 결제창을 실측하고, 발급사 쪽 조건과 이해 단계 아티팩트를 더합니다. L2는 AIR 범위 권한 위에서 동작하도록 설계해 같은 방향의 한국형 앞단이 됩니다.

**Q10. 네이버도 멤버십 혜택 추천하고 결제까지 붙이면요?** 네이버 에이전트는 네이버 안의 가격을 봅니다. 저희 해자는 플랫폼을 가로지르는 중립성, 발급사 쪽 조건, 근거 공개, 그리고 광고·제휴 수수료 없음입니다. 네이버가 브라우저 조작 + 사용자 최종 승인 구조를 택한 것은 이 방식의 실현 가능성을 보여주는 근거이기도 합니다.

**Q11. 개인정보는요?** 화면 해석은 사용자 기기에서 하고, 금액·조건만 구조화해 저장하며 카드번호·주소는 기기 밖으로 보내지 않습니다. 로드맵에서는 AIR Identity의 선택적 공개로 "이 카드 보유"만 증명합니다.

**Q12. 프롬프트 인젝션은요?** 에이전트형 브라우저가 가짜 쇼핑몰에서 결제하거나 숨은 지시에 따라 구매한 사례가 보고됐습니다(Guardio 2025, SecurityWeek). 저희는 결제 자격증명을 입력하지 않고 결제 버튼을 누르지 않으므로 피해 범위가 제한됩니다. 상품 페이지 텍스트는 출처 라벨을 붙여 데이터로만 취급합니다.

**Q13. 백엔드 LLM이 다 비슷하면 에이전트도 다 비슷하지 않나요?** (Animoca 강의의 문제 제기) 맞습니다. 그래서 저희 차별점은 모델이 아니라 무엇을 보느냐에 있습니다. 하나는 선택 후 사용 환경을 이해하는 것(KVM이라면 연결 구성과 추가 구성품)이고, 다른 하나는 사용자 로그인 결제창에서 실측한 진짜 가격입니다. 신원 인증은 AIR 같은 인프라가 맡을 영역이고, 저희는 그 위에 올라가는 앞단입니다.

**Q14. 오늘 강의에서 나온 네 가지 질문(신뢰·보안·분쟁·닫힌 결제)에 답해 보세요.** 신뢰: L1에서 판매자가 보는 주체는 사용자 본인입니다. 보안: 카드·비밀번호·PIN을 받지 않습니다. 분쟁: 사용자가 판매처 결제창에서 직접 승인하므로 기존 카드 거래의 증거가 남고, 여기에 결정 영수증을 더합니다. 닫힌 결제: 웹으로 링크아웃하는 대신 사용자 앱의 실제 결제창까지 데려가 금액을 실측하고 멈춥니다. 국내 레일이 열리면 L2에서 AIR 위의 승인 위임형으로 연결합니다.

## Conclusion

이번 조사에서 가장 쓸모 있는 발견은 **표준 스스로가 우리 정직성 원칙을 정당화한다**는 점이다. UCP는 구매자 주장을 provisional, 검증된 회원가를 verified로 나눈다. AP2는 비결정적 에이전트가 조립하고 결정론적 코드가 검증하며, 검증할 수 없으면 사람에게 돌아가게 한다. 결제망은 청구 금액만 강제할 수 있어서, 청구할인·실적·포인트를 반영한 '실질가'는 L2가 완전히 표준화된 미래에도 **사용자 편 에이전트만 검사할 수 있는 숫자**로 남는다. 그러니 "UCP가 와도 남는 가치"는 방어 논리가 아니라 스펙 구조에서 나오는 결론이다. 확인됨/추정/미확인 라벨, 결제 직전 멈춤, 결정 영수증은 겸손한 타협이 아니라 **업계 표준 의미론과 맞춘 기능**으로 발표하는 편이 심사기준 [A-안심 위임]과 [논리·실현]에 더 강하게 닿는다. 오늘 강의의 틀로 다시 보면 이 설계의 성격이 더 선명해진다. Google의 5단계와 6가지 요소 가운데 L1이 직접 맡는 것은 의도 정의(기준 발견), 결제창 실측, 관측·감사뿐이다. 서명·퍼실리테이터·정산·KYA는 사용자 본인 세션과 기존 카드망에 남겨둔다. 다시 말해 **가장 적게 위임하면서 가장 많이 이해시키는 설계**다. 그리고 Animoca가 말한 "결국 신뢰의 문제"에 대해, 신원 인프라가 아직 국내에 깔리지 않은 지금 할 수 있는 가장 정직한 답이다.

남은 긴장도 분명하다. 한국 1·2위 플랫폼은 자체 에이전트를 키우면서 외부 에이전트를 제한하고, 네이버는 우리와 같은 "브라우저 조작 + 최종 승인" 구조를 연내 직접 내놓겠다고 했다. 판매처를 가로지르는 구매자 측 에이전트는 플랫폼이 **구조적으로 채우지 않을 공백**이지만, 동시에 **구조적으로 견제받을 위치**다. 해자는 기술 접근권이 아니라 중립성(수익원 없음), 근거, 발급사 쪽 조건이다. 장기 경로는 화면 실측에서 MCP·UCP 어댑터로, 그리고 발급사 토큰과 AIR 범위 권한 위의 L2로 옮겨가는 것이다. 오늘 시연에서는 KVM 하나로 "표시가 순위와 진짜 가격 순위가 갈리는 순간"을 팀이 직접 측정한 표본으로 보여주는 것이 어떤 통계보다 강한 증거가 된다.
